## Contract for RED
`confirm(request, publicationId, input)` accepts the existing strict `parseConfirmFoxyPublication` shape: requestId, publicationRevision, classroomRevision, confirm=true. Actor comes from Foxy UoW and must still be a verified teacher; no client file/material IDs, digests, snapshot or proof accepted. Confirm targets only the publication owner's existing READY row. Successful response is a public DTO with publicationId, materialId and the resulting publication/classroom revisions; no storage key, file ID, hash or source snapshot. Exact shape should be frozen by architect/test runner before implementation.

Each call reauthenticates and rechecks owner, accessible nondeleted conversation and destination ownership. Under one DB transaction, read source classroom identity without locks as a hint, then use the following ordering and revalidate every hinted relationship after locks: (1) user FOR UPDATE as existing `createFoxyUnitOfWork.run` and publication allocator; (2) source and destination classrooms FOR UPDATE in sorted UUID order as `publication-completion.scopes` and allocator (one lock if same); (3) resource and conversation FOR SHARE with source identity and revision recheck; (4) publication FOR UPDATE with owner/destination recheck; (5) applicable existing unit and topic FOR SHARE in hierarchy order as `LibraryService.materialAssociation`; (6) file, upload and custody locked in the same explicit deterministic order as shared completion implementation, after publication lock, and optionally existing material row if needed. Library mutation/cleanup start with classroom lock (`classrooms/context.ts`, `library-cleanup.ts`); file scope authorization/cleanup also lock classroom first (`files/store.ts`, `files/cleanup.ts`). No nested transactions; call shared transaction-level primitives or port their invariant checks with a single documented lock policy. Note existing completion uses `FOR UPDATE OF p,f,u,c` in one query and does not independently specify file-row lock order; architect must reconcile with file receive/cleanup before claiming deadlock freedom. Obtain current class owner and conversation state after locks, do not trust earlier hint.

After authorized publication lock, look up confirmation request by (ownerId, requestId) before requiring current publication/classroom revisions. Hash canonical publicationId plus all parsed input fields (including revisions and explicit confirm). For same hash, if referenced material is still live and accessible return original successful receipt without writes, including after later classroom revision or archive. If material is soft-deleted or its blob is deleted, return the same opaque NOT_FOUND as inaccessible resource; do not disclose material ID, content, deletion details, or resurrect it. If context/source/destination ownership revoked or conversation deleted, deny without replay data. Different hash for used request ID returns CONFLICT after authorization, before CAS. A new request against PUBLISHED returns CONFLICT; no duplicate material. Replay must serialize with library deletion under classroom lock and check live material, rather than trusting cached JSON.

For a new request only: require destination active, state READY, exact publicationRevision and classroomRevision, source resource revision still equal snapshot revision (same freshness policy as `publication-completion.ts`), and unit/topic still belong to classroom with correct hierarchy. Recheck file as in completion: association on publication, correct owner/classroom, no blob deletion, pdf and expected size, material purpose with null target, upload completed, custody ready, approved/clean and all stored digests equal frozen artifact digest. Do not accept caller proof. Check file is not linked by any material including soft-deleted rows, and guard concurrency at DB level. Insert material using publication's frozen title/unit/topic and file; advance classroom revision once; transition publication READY→PUBLISHED and increment revision; insert request receipt with resulting revisions and material ID. Commit all atomically. A uniqueness conflict or any failure must roll back every write. No material publication on worker READY alone.
