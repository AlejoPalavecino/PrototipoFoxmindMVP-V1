# FoxMind visual reference index

See the [design catalog](design/INDEX.md) for the relationship between these references and later directions.

These repository-local screenshots define the frontend's visual direction: a warm orange identity, the fox character, rounded white surfaces and clear educational workflows. They are references, not implemented screens or a source of new product rules. The [functional specification](foxmind-v1-functional-spec.md) takes precedence for permissions, data, states and behavior.

## Current source and availability

The current reference set contains **29 PNG screenshots in `docs/references/`**, all visually reviewed. The inventory below links directly to those files relative to this document. The supplied names have been preserved; no screenshots were renamed, moved or edited in this review.

All 29 captures use wide desktop compositions (source widths 1,122–1,672 pixels). Some are tall full-page forms, up to 3,510 pixels high; height alone does not make a capture mobile. ## Visual language to preserve

### Composition and hierarchy

- Keep an airy, very light cool/neutral background with white content surfaces, generous outer gutters, rounded corners, fine cool-gray borders and diffuse shadows. Avoid heavy dark panels or dense dashboard chrome.
- Place the fox/wordmark at the left of a rounded top navigation bar, navigation near the center and account/notifications at the right. Global selected navigation is an orange pill; classroom tabs use orange icon/text and an underline.
- Classroom pages stack breadcrumb, a cover/thumbnail plus classroom title/context and tabs, then the main content card. Use the selected predefined cover artwork; photographic examples do not authorize cover uploads or require photography-only classrooms.
- Use large, bold, rounded-feeling dark headings and blue-gray supporting text. Distinguish page title, section title, labels and metadata clearly. Exact font identity is not established by a generated screenshot.
- Home may be more expressive: warm peach/orange hero areas, fox artwork and larger visual cards. Forms, tables, correction and evaluation should remain quieter and task-focused, without dropping the brand.

### Components

- Primary actions use orange, sometimes with a soft warm gradient and gentle shadow; secondary actions use white/pale surfaces, subtle outlines and dark text. Keep pill navigation distinct from rounded rectangular form buttons.
- Cards, fields, upload zones, option rows and dialogs share softened corners. Maintain visible boundaries and generous click/touch areas rather than flattening everything into text.
- Use consistent rounded/outline-style icons, often on pale icon tiles. Activity types can use peach, lavender or mint chips while orange remains the navigation/action accent.
- Keep tables light: restrained headers, thin row separators, compact status pills and progress bars. Identify states with text/icons as well as color; do not invent pass/fail thresholds.
- Dialogs use a centered light panel over a subdued background, clear title, labeled inputs, close control and a separated action area. Wizard steps use numbered markers and a clear active/completed progression.
- Preserve the layout of repeated question cards, file rows and correction/result sections in the long forms; these are not instructions to force a tall page into a fixed-height viewport.
- Evaluation-taking prioritizes the question and large answer targets. Show real save state, question progress and previous/next/review actions; orange means current/selected, not necessarily correct.

### Identity and asset readiness

- Preserve the original fox identity. Full-page screenshots are layout references, not reusable logo files, hero artwork or cover assets.
- A standalone original logo and separate illustration/cover assets are not included in this screenshot inventory. Prepare those separately before production use; do not crop UI screenshots into final interface assets.
- Replace pictured participant headshots with the confirmed automatic initials where appropriate. Screenshots do not authorize avatar uploads or public profiles.
- Colors, typography and dimensions must be implemented as a consistent system, not guessed independently for each screen. Existing hex/font suggestions in specification section 13 remain working proposals, not pixel measurements extracted here.

## Written decisions that override image details

| Image detail | Authoritative interpretation |
|---|---|
| Exclusive teacher/student global views; fixed profile role | Use `Enseño` and `Estudio` blocks in Mis Aulas and Home summaries for one account, with creating and joining available and no global role switch. |
| `Año` | Use `Ciclo lectivo`, meaning calendar/academic year, not level. |
| Creation forms/deadlines without a timezone | Suggest the browser timezone at creation and allow teacher selection; the timezone is fixed afterward in V1. Identify it beside deadlines. Reject nonexistent local times; for repeated local times, show both UTC offsets and require explicit selection. |
| Code dialog appearing to enroll immediately after entry | First-time code enrollment must preview classroom name, subject, division, academic year and teacher, then require explicit user confirmation; no additional teacher approval is needed. |
| Student Home progress measured in classes | Teaching progress is based on topics marked as taught; attendance/class sessions were not defined. |
| 10 MB upload limit or 1000-character observation limit | Plans/instructions allow 20 MB per file; Library/submissions allow 50 MB per file, at most 5 files per submission and no extra aggregate cap beyond 250 MB, subject to quota. Observations, feedback and Muro text allow 5,000 characters, not the generated 1,000. |
| Broad Office labels or upload controls implying additional formats | Plans/instructions accept `.pdf` and `.docx`; Library/submissions additionally accept `.pptx`, `.xlsx`, `.jpg`, `.jpeg`, `.png` and `.zip`. Legacy `.doc`/`.ppt`/`.xls` and macro-enabled `.docm`/`.pptm`/`.xlsm` are excluded in V1. |
| A 10-point evaluation | Example only; normalize grades to 0–10 regardless of available points. |
| `En 3 días` alongside a submission after the deadline | Contradictory generated copy; use coherent dates and status. |
| Reply composer with another participant's avatar | Composer identity must match the logged-in author. |
| `Marcar como siguiente` on an already-next topic | Avoid the redundant action for that state. |
| Editable controls on the student Plan screenshot | Students only consult topic states; remove checkboxes and teacher state-changing actions from the student view. |
| Grades such as `7,5` or suggested pass/fail labels | Published grades and averages use two decimals (`7,50`); do not infer `Aprobado` / `Desaprobado` from a number. |
| Classroom-wide grade average | Use the confirmed mean of individual published-grade averages, not a pooled weighted mean. |
| Profile image or read-only example fields | Muro author identity uses first/last name and automatic initials; no avatar upload, public profile, exposed email, email editing or global role selector is approved. |
| Bright orange with white text | Preserve the aesthetic, but verify actual contrast; generated pixels are not an accessibility guarantee. |
| Classroom cover illustrations or image-upload affordances | Teacher selects from predefined illustrations; classroom cover uploads are not part of V1. |
| Creation form fields that appear optional, categorical or disposable | All classroom fields, the plan and at least one unit/topic are required at completion; Materia/División are free text and unfinished creation is a private recoverable draft. |
| Activity creation that appears to publish immediately | Save private drafts and publish explicitly; only published activities are visible to students and generate new-activity notifications. |
| TP instruction file or student attachment shown as universally required | TP instruction may be observations, PDF/DOCX or both. The teacher configures whether student attachments are mandatory. |
| Selection question editor permitting only one multiple-choice key | Single-choice has exactly one correct option; multiple-choice has at least two, with at least two options for either type. |
| Reopened attempt or correction history layout | Prefill prior responses/attachments without altering the original; attempts are newest first and grade-correction audits are teacher-only. |
| Generic enrollment failure that navigates elsewhere | Stay in the form with a generic notice; do not redirect or enroll a different invited account. |
| Extra settings, menus or illustrated metadata | Do not infer new product capabilities from decoration or generic UI conventions. |
