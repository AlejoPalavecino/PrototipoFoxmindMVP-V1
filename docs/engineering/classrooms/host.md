# Integrated P5 API host

P5 is an explicit opt-in of the accepted P3/P4 application, not the isolated preview host. The complete route/payload contract remains in [classrooms](classrooms.md). Existing P3 identity and P4 file endpoints remain mounted unchanged.

## Configuration

The normal identity, captured-mail and private-file configuration is required. No environment file is read or generated by this integration.

| Variable | Required value |
|---|---|
| `CLASSROOMS_ENABLED` | `1`; absence disables P5 without changing P3/P4 |
| `CLASSROOMS_QUOTA_BYTES` | Explicit positive decimal bigint, at most `9223372036854775807`; no production default |
| `CLASSROOMS_SIGNING_KEY` | Durable, canonical unpadded base64url encoding of 32 random bytes |
| `CLASSROOMS_DELIVERY_KEY` | A different durable 32-byte key in the same encoding |
| `FILES_ENABLED` | `1`, with the complete existing P4 storage/scanner/draft-quota configuration |
| `APP_ORIGIN` | Existing exact trusted P3 web origin; also owns invitation links and mutation Origin checks |
| `MAIL_SMTP_PORT` | Existing captured SMTP configuration; invitation sender connects only to `127.0.0.1` |

Keep both P5 keys stable across restarts and out of source, logs and client configuration. Uniform-byte, malformed, missing and equal keys fail startup. Key rotation, a production mail provider and a paid production quota remain separate decisions.

## Security and files

`/api/v1/classrooms` and its subroutes are installed before general JSON parsers. The host reads the actual `foxmind_session` cookie, applies existing P3 IP/session admission once per accepted request and enforces verified email. `POST` and `PATCH` require exact Origin plus session-bound CSRF; the authentication bridge also guards `PUT` when invoked by a trusted caller. Fake account headers and duplicate/malformed cookies grant no identity.

The domain authenticates again inside its existing transaction and after the user lock. Both checks use P3's `authenticateSession`, digest, database clock and fixed session policy. They neither increment ingress counters nor extend either session deadline. P3 revocation takes the same user lock. Known P3 errors retain their public status/code and `Retry-After` where applicable; arbitrary SQL errors remain sanitized.

Classrooms use the **same** integrated `FileService.store`. Publication still invokes P4's existing transactional promotion, custody/security/quota checks and source/destination locks; there is no alternate upload store or permissive file authorization. Trusted P4 session revalidation failures retain their original identity denial. Unsupported attempt writes remain denied by the unchanged P4 bridge.

## Invitation lifecycle

One `InvitationDeliveryWorker` owns periodic dispatch in each application instance. Existing encrypted durable jobs, generation/expiry/archive checks, bounded retry/lease policy, five-second periodic interval and SMTP deadlines remain unchanged. The sender reuses the existing local captured-SMTP adapter and P3's trusted SMTP port, not a new provider. Links target `/mis-aulas?invitacion=<id>` and still require the current verified recipient's explicit acceptance.

The root module drains the invitation worker alongside identity mail and file cleanup **before Prisma teardown**. Worker startup and shutdown are idempotent; the root lifecycle closes the owned sender once after drain. A fresh application instance reconstructs the worker from durable jobs. Startup failure also closes allocated storage/sender resources. `app.get(InvitationDeliveryWorker)` finds the sole worker for trusted test synchronization; no HTTP stop-worker endpoint or production testing flag is introduced.

## Verification boundary

`node scripts/build-api.mjs` retains its existing 30-second total build budget. Focused deterministic checks:

```text
node --test --test-concurrency=1 tests/p5-host.test.mjs tests/p5-session-bridge.test.mjs tests/p4-host.test.mjs tests/p4-session-bridge.test.mjs tests/p5-http.test.mjs tests/p5-policy.test.mjs
```

These tests cover host/session composition, rejection/data-effect invariants, worker ownership/drain and existing P4 transport contracts. They do not replace the coordinator's real PostgreSQL/S3/scanner/captured-email/browser/restart proof or independent verification.
